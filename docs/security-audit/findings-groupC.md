# Group C findings

Modules: projects, tasks, tasks_template, calendar, files, forums, projectdesigner, macroprojects, igantt, ical, closure, initiating, monitoringandcontrol.

Paths relative to .. Every line was read directly.

Framework notes confirmed for this group:
- `dPgetCleanParam` = htmLawed safe mode; it leaves quotes, parens, `--`, `OR` intact, so it gives no SQL protection and no attribute/JS-context protection.
- `CDpObject::bind()` / `bindHashToObject()` copy POST values onto every declared object property with no HTML encoding; `db_insertObject`/`db_updateObject` only SQL-escape on write; `load()` does not HTML-encode on read. So any field set via `bind($_POST)` and later echoed without `$AppUI->___()` / `htmlspecialchars()` is stored XSS.
- `$q->addWhere('col = ' . $v)` and `"col = $v"` are string interpolation (injectable); `addOrder($var)` cannot be parameterized.

## Verified-safe (checked, not reported)
- modules/files uploads: `moveTemp()` uses `move_uploaded_file` to a server-generated `uniqid(rand())` name (do_file_aed.php:126), so the stored filename is not attacker-controlled; download path in fileviewer.php is gated by getAllowedRecords/setAllowedSQL + `(int)file_id`. The unlink/copy traversal risk exists only via editing an existing record's bound `file_real_filename`/`file_project`, but those are overwritten on store and `check()` intvals file_project; real_filename is never re-bound from a form field in normal flow. Left as residual hardening note rather than a finding.
- modules/files/do_folder_aed.php, do_file_co.php, do_files_bulk_aed.php: destructive ops go through CFile/CFileFolder delete() which call parent canDelete() (CDpObject::canDelete checks checkModuleItem). OK.
- Most `addWhere('x = ' . $var)` in projects/tasks/macroprojects class files use `$project_id`, `$user_id`, `$company_id`, `$department` that are intval'd at the entry points (gantt.php:17-20, reports.php:6, view.php:8, index.php casts). project_status update (index.php:26) binds via `?`. These are safe.
- igantt.ajax.php / igantt.ajax.class.php: not referenced by any include in the active module (index.php uses vw_igantt.php + update_task_dates.php); appear to be dead XAJAX code. vw_igantt.php builds JSON via json_encode (safe) and `task_project = $project_id` with project_id intval'd at :7.
- tasks_template/do_insert_tasks_template.php: `$tasks_template_id` from request used in interpolated SQL (`tt.tasks_template_id = '$tasks_template_id'`, lines 22,74), BUT the include line in setup.php points to a misspelled path `modules/tasks_tempalte/...` (setup.php:21) so the handler is not wired in; also only reachable where `$obj` is a loaded task/project. Flagging as latent SQLi if ever wired: lines 22,74 interpolate request value — intval it.

## Patterns (systemic)
1. **addOrder with request-derived sort/orderdir, inconsistently whitelisted.** projects/index.php and its dept/admin tabs correctly `in_array(...,$valid_ordering)` the orderby, but forums (index.php, view_topics.php, view_messages.php, view_pdf.php) and closure tabs pass `sort`/`orderby`/`orderdir` to addOrder with no whitelist. Recommend a single `dpValidateOrder($col,$dir,$whitelist)` helper.
2. **dosql write handlers in the smaller modules omit permission checks.** initiating (perm check commented out), forums do_forum_aed/do_post_aed, projectdesigner do_task_bulk_aed, igantt update_task_dates (module-wide not per-item) all mutate/delete by id with weak or no `getPermission(...,$id)` — combined with the known branch-wide "dosql via GET, no CSRF token" this is CSRF-to-delete/IDOR. The core objects these call (CForum, CForumMessage, CInitiating) override delete() WITHOUT an ACL check, unlike CDpObject::delete.
3. **Raw echo of DB-stored, bind()-populated fields.** `bind($_POST)` + `db_*Object` never HTML-encode, and `load()` does not encode on read, yet views echo `*_description`, `*_name`, `participants`, `event_title`, `message_title`, `file_co_reason` sometimes through `$AppUI->___()` and sometimes raw — the raw ones (listed above) are stored XSS. No module here consistently encodes on output.
4. **Report date filters (`log_start_date`/`log_end_date`) interpolated into WHERE** in projects/overall.php and macroprojects/overall.php without intval, even though sibling reports cast them — copy/paste divergence.
5. **unserialize(urldecode($_GET[...]))** in all four monitoringandcontrol/grafico chart scripts, which also lack any auth bootstrap — the single worst issue in this group.
