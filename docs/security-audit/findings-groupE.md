# Group E findings — dotproject_plus, timecard, timeplanning, timesheet, timetrack, human_resources, resources, resource_m, holiday, mileagelog, testing

Repo: . (branch dotproject_plus-module-integration-in-the-core). All paths absolute. Severity per brief: pre-auth = CRITICAL, any logged-in user = HIGH, admin-only = MEDIUM.

Scope notes for dotproject_plus:
- `modules/dotproject_plus/dotproject_plus/` is a stale nested copy of the upstream module (differs from the top-level files). It is NOT routed (index.php resolves `?m=dotproject_plus&a=X` / `dosql=X` to the top-level dir, and `checkFileName()` strips `/`), so only top-level files are reported. It should be deleted on this branch to avoid confusion.
- `modules/dotproject_plus/changed_files_from_other_modules/*` are reference copies, not included anywhere; not audited as live code (they differ from the real core files).
- `modules/dotproject_plus/tasks.php` is byte-identical to `modules/tasks/tasks.php` (core) — core group owns findings there (e.g. `searchtext` state interpolated into LIKE at line 292).
- `projects_tab.planning_and_monitoring.php` and `projects_tab.execution.php` are included by core `modules/projects/view.php` (tabs 1 and 2). `companies_tab.Projects.php` is included by core `modules/companies/view.php`. So the view-side bugs below fire from `?m=projects&a=view` / `?m=companies&a=view`, reachable by any user with project/company view permission.
- No dosql file in dotproject_plus calls `getPermission()`/`canEdit()`/`canDelete()`. The ids they receive are never intval'd and never checked against the project the user may edit.

## Patterns (systemic across group E)

1. **No authorization anywhere in the dosql layer.** Not one dosql file in dotproject_plus (16 files), timeplanning (6), timetrack (2), timesheet (1), human_resources (4) or holiday calls `getPermission`/`canEdit`/`canDelete`/ownership. Where `canDelete` exists it is commented out (HR, testing) or overridden to `return true` (all four HR classes). Combined with the known core "dosql on GET, no CSRF" issue, every record in `tasks`, `project_eap_items`, `company_role`, `timetrack_data`, `human_resource_*`, `holiday` is deletable/rewritable by any logged-in user.
2. **The shared timeplanning model/controller layer concatenates every id into `addWhere`** (`wbs_item`, `wbs_item_activity_relationship`, `wbs_item_estimation`, `company_role`, `project_minute`, `activities_mdp`, `controller_wbs_items`, `controller_wbs_item_activity_relationship`, `controller_activity_mdp`, `controller_project_minute`). dotproject_plus, timeplanning tabs and dosql files all call into it with raw `$_POST`/`$_GET` values; only `project_task_estimation.class.php:45` casts. Fixing `intval()` in those ~12 model methods closes roughly 20 of the HIGH rows above at once. Inserts/updates are safe (`addInsert`/`addUpdate` bind).
3. **Project-view tab files re-read `project_id` raw from `$_GET`** (dotproject_plus `projects_tab.*`, timeplanning `projects_tab.*`) even though `modules/projects/view.php` already intval'd it for the ACL check. The intval'd value satisfies the permission check on a project the attacker can view; the raw suffix is then injected. One-line fix: delete the re-read.
4. **`$_GET` id → `$AppUI->setState()` → SQL in another file** (timecard `user_id`/`company_id`/`tab`, mileagelog `user_id`, testing `project_id`): the injection is sticky for the session and the source is invisible from the sink file. PHP 8 string-vs-int comparison (`"1 OR 1=1" > 0` is true) defeats the `> 0` guards used in timecard and testing.
5. **No output escaping as a rule.** Every module in scope echoes DB-stored names/descriptions/notes and many request params raw, including in attribute and JS-string contexts (dotproject_plus `showWBSItemEdit(<?php echo $_GET[...] ?>)`, timeplanning `addItem(..,"<name>")`, HR `deleteRole('<name>')`, HR `href=<lattes_url>`). Only the holiday/principles edit forms, `companies_tab.Projects.php` and `dPformSafe()` in a few HR edit forms escape.
6. **Admin config forms write raw POST into auto-required PHP files** (timecard/configure.php, mileagelog/configure.php): persistent RCE for a system admin or via admin CSRF.
7. **Dead/broken legacy code hides live bugs**: PHP4 constructors (testing), `&new` parse errors (timecard vw_newlog/vw_log_update), `print_r(...);die` (mileagelog), array-access-on-object (mileagelog), dormant `runFeedbackTriggersEvaluation()` (dotproject_plus) and the stale nested `dotproject_plus/dotproject_plus/` copy. Each of these has raw-SQL/authz bugs underneath that become live as soon as the "bug" is fixed.
8. **Vendored third-party PHP in the webroot** (timeplanning `wireit` examples/backend) with no `DP_BASE_DIR` guard: pre-auth XSS echo endpoints, an unauthenticated file writer, hard-coded `root/root` DB creds.
